# Saved pre-simulations

The pre-simulation player can save a completed run and load it again without
rerunning the mechanical or electrical model. This is intended for repeatable
review, exchanging results, and inspecting a run in general engineering tools.

## UI workflow

1. Select the topology, startup method, sequence, parameters, and duration.
2. Run **Pre-simulate parameters** and wait for completion.
3. Select **Save Pre-Simulation** and choose a CSV filename.
4. Keep the generated `.csv` and `.json` files together.
5. Later, select **Load Pre-Simulation** and choose either member of the pair.
6. Use the normal Play/Pause and playback-speed controls.

**View Replay Parameters** displays the saved configuration as read-only JSON.
The application's current editable Parameters values are not overwritten when a
run is loaded. During replay, drawings and engineering context use the saved
parameter snapshot; returning to a live run uses the current application values.

## File pair

For a selected filename such as `lowering-test.csv`, the simulator writes:

- `lowering-test.csv` — all time-series replay data;
- `lowering-test.json` — metadata, configuration, and the CSV column schema.

The CSV is UTF-8 with a byte-order mark for convenient Excel import. It is a
normal wide table and can also be read with Python, MATLAB/Octave, R, or other
CSV tools. Boolean values are written as `true` and `false`. Nested telemetry,
including power-flow diagnostics, is flattened into columns using `__` between
path elements.

Frequently used signals receive explicit engineering names, including:

| CSV column | Meaning | Unit |
|---|---|---|
| `time_s` | Replay-frame time | s |
| `load_position_m` | Lowering travel | m |
| `load_speed_m_min` | Load lowering speed | m/min |
| `motor_rpm` | Motor-shaft speed | RPM |
| `synchronous_speed_rpm` | Electrical synchronous speed | RPM |
| `ac_voltage_v_ll_rms` | AC line-to-line RMS voltage | V |
| `motor_current_a_rms` | Machine RMS current | A |
| `motor_active_current_a_rms` | Active-current component | A |
| `motor_reactive_current_a_rms` | Reactive-current component | A |
| `generated_active_power_w` | Electrical power exported by the machine | W |
| `ac_frequency_hz` | Estimated AC-bus frequency | Hz |
| `frequency_command_hz` | Scalar V/f frequency command | Hz |
| `magnetic_flux_wb_turn` | Estimated magnetic flux linkage | Wb turn |
| `dc_link_voltage_v` | Main DC-link voltage | V |
| `rectifier_dc_power_w` | Rectifier DC output power | W |
| `resistor_power_w` | Brake-resistor power | W |

The CSV also contains the replay state's position, angle, angular velocity,
ground-contact and impact values, plus frame-level brake, motor, inverter, and
capacitor states. All remaining readings are retained even when they do not
have a specially shortened column name. The JSON `csv_schema` maps every CSV
column back to its exact replay-dictionary path, data type, unit, and any unit
conversion applied for the CSV.

## Complete parameter snapshot

The JSON `parameters` object is generated by iterating over the complete
`Parameters` dataclass. It is not a manually maintained subset. Each entry
contains:

- parameter name;
- exact value used at the start of the run;
- engineering unit;
- meaning and estimation status;
- configured minimum and maximum.

Consequently, newly added `Parameters` fields are included automatically. The
snapshot covers the mechanical system, machine equivalent circuit, capacitors,
scalar V/f controller, battery and converters, auxiliary and main DC links,
rectifier, chopper/resistor, brake, contactors/precharge, charger, automatic
sequence, numerical settings exposed as parameters, and initial conditions.

The separate `run_configuration` object records configuration outside the
`Parameters` dataclass. It includes the model class, excitation and startup
modes, UI topology selection, automatic-profile selection, requested frequency
sequence, controller inputs, model switch/configuration values, initial model
and electrical state, requested duration, physics step, maximum electrical
substep, telemetry interval, and display timing.

## Loading and playback

Loading performs file parsing and reconstructs the lightweight `ReplayFrame`
objects used by the existing player. It does not construct a replacement run,
call the model's `step()` method, or reset the live model. Saved telemetry drives
the following directly:

- rotor and load position;
- magnetic-field animation;
- active and reactive power-flow animation;
- plots and numerical telemetry;
- brake command and physical state;
- contactor, controller, fault, and topology states.

The paired JSON file must be present because it defines how CSV columns map back
to the nested replay representation.

## Format identification and integrity

Current files use:

```json
{
  "format": "elowering-pre-simulation",
  "format_version": 1
}
```

The metadata also stores the telemetry filename, SHA-256 checksum, frame count,
duration, telemetry interval, parameter type, complete parameter snapshot, run
configuration, and column schema. The loader rejects unknown versions, missing
columns, invalid timing metadata, frame-count mismatches, and CSV files whose
checksum no longer matches. This prevents a plausible-looking but incomplete or
mispaired replay from being shown silently.

To inspect or transform a saved run, operate on a copy of the pair. Editing the
CSV intentionally invalidates the checksum; update tooling should emit a new
versioned pair rather than modifying an archived result in place.
